## 1. Collect real examples

Sources, best first:
1. **Real inputs** from the workflow (tickets, documents, questions), anonymised as needed.
2. **Failures** people have seen ("AI fails" channel, [M1](/ai-native-teams/m01-foundations/limits/#team-practice)).
3. **Edge cases** domain experts know about.
4. **Synthetic examples** generated by AI to fill gaps, reviewed by a human.

## 2. Define what "good" means per example

| Approach | When | Example |
|---|---|---|
| **Exact / rule-based** | Clear right answers | Category equals `BUG`; JSON valid; total equals 1,240.50 |
| **Must include / must not include** | Key facts or forbidden content | Mentions the 30-day refund window; never mentions competitor names |
| **Rubric** | Open-ended outputs | Accurate (1–5), complete (1–5), tone matches guidelines (pass/fail) |
| **Reference answer** | Comparable outputs | Similar in meaning to the expert's answer |

Write criteria **before** looking at model outputs, so you're not grading on a curve.

## 3. Cover the space

Make sure the set includes:
- **Typical cases** (most of the set).
- **Hard cases:** ambiguous inputs, long inputs, conflicting information.
- **Should-refuse / should-abstain cases:** out of scope, missing information.
- **Adversarial cases:** injection attempts, attempts to extract restricted data.
- **Slices that matter:** languages, customer segments, product areas, so you can see if quality is uneven.

## 4. Store it simply

A spreadsheet works to start:

| id | input | context/docs | criteria | expected | slice | added because |
|---|---|---|---|---|---|---|
| 017 | "Can I get a refund after 45 days?" | refund-policy.md | Says no (30 days); offers escalation path; cites policy | No, with escalation | refunds | Bot said yes in prod, 2026-10-02 |

As it grows, move to an eval tool (promptfoo, Inspect, DeepEval, Braintrust, LangSmith, Phoenix and others, see the [tools landscape](/ai-native-teams/reference/tools-landscape/)) that can run the set automatically and track results over time.

## 5. Run it as a habit

- **Before launch:** agree a threshold per criterion.
- **On every change** to prompt, model, tools, retrieval or instructions.
- **On a schedule** (e.g. weekly), because providers update models and your data changes.
- **After incidents:** add the failing case, fix, re-run.

## Avoid these

- **Testing only happy paths.**
- **Overfitting:** tuning the prompt until the 30 examples pass while real-world quality doesn't improve. Keep a held-out set you don't tune on.
- **Stale sets** that no longer reflect real usage. Refresh from production samples.
